# Feature Implementation Spec: Admin-only Temas tab: list the song catalog and add, edit and delete songs

## Source Feature

- `id`: admin-catalog-tab · `area`: feature-catalog (also backend, `:core:data`, `:app`, `:konsist-test`)
- `depends_on`: catalog-repository-cache, apps-script-write-auth, admin-passphrase-login, bottom-navigation,
  core-assistant-module (all `accepted` at planning time)
- `status`: not_started at planning time
- `source`: `feature_list.json`; user decisions of 20 October 2026 (1–5, below as **D-30**); D-04, D-08, D-12, D-13,
  D-15, D-16, D-17, D-24, D-28

## Goal

In admin mode a fifth bottom tab, **Temas**, between Jams and Info, lists the catalog. The admin adds a song (title,
artist, default key), edits those three fields, and deletes a song after confirming. Deleting is refused, with the
reason, while the song is in the upcoming jam or a held-back future jam; a song only in past jams can be deleted (jam
tabs keep plain-text title/artist copies). Every write is a guarded Apps Script action that validates on the server,
reached through a `:core:data` repository function (D-13). Room follows only a confirmed answer, then the catalog is
refreshed. Musicians never see the tab.

The slice has two parts done in order in one pass (as `admin-add-song-to-setlist` did): **Part A** server +
`:core:data` + Konsist + docs + migration guide; **Part B** `:feature:catalog` + `:app` + DESIGN.md. Not split in
`feature_list.json`: one entity, one flow, and the UI is not useful without the contract.

## Non-Goals

- The app never writes `tempo`, `etiquetas`, `dificultad`, `songsterr_id` or `id` after creation (decision 3, 5).
- No change to any jam tab or `Jams` row: editing a title does not rewrite the copies in jam tabs (they are a
  fallback only; the catalog is authoritative for display); editing `tono_default` never changes any jam's `tono` (D-08).
- No assistant tool, prompt or proposal change; the agent stays read-only (D-24).
- No bulk import, no undo, no restore of a deleted song's id, no enrichment fetch (D-09), no musician view.
- No Room schema change, no new navigation route outside the tab, no write to the real Sheet during verification.

## Job Story

When I add a song to the jam's repertoire or spot a typo, I want to fix the catalog from my phone, so that I do not
need to open the Sheet on a laptop, without being able to break a list that is already planned.

## Users And Permissions

Admin only. The tab is drawn only when `AdminSession.observeIsAdmin()` emits `true`; the presenter also returns
`Hidden` for a musician (defence in depth). The local flag authorizes nothing: every action passes the router's
passphrase guard and the script lock (`handlePost`).

## Decisions (recorded defaults; the user's five decisions are settled)

- **C1 Module.** New `:feature:catalog` (package `com.bbbjam.feature.catalog`), depending on `:core:ui` and `:core:data`
  only. Named after the domain, not the role, so D-15 holds (no `:feature:admin`); its only screen is admin-gated.
- **C2 Ids are generated by the server.** The server holds the authoritative `Catalogo` (hand edits included, and rows
  the client mapper rejected) and runs under the script lock, so uniqueness is decided atomically; a client cache can be
  stale and two devices could pick the same id. The client never sends an id on create.
- **C3 Slug.** `songSlug_(text)`: NFD, drop U+0300–U+036F, lowercase, every run of characters outside `[a-z0-9]` → one
  `-`, trim `-`. `Café Madrid` → `cafe-madrid`, `Ñandú` → `nandu`, `7/4` → `7-4`. Candidate order: `slug(title)`; if
  taken, `slug(title)-slug(artist)` (sheet-schema rule); if still taken, that plus `-2`, `-3`, … (smallest free).
  **Taken** = every trimmed `id` cell of `Catalogo` (valid or not) ∪ every `id_tema` of the jam tabs named by a `Jams`
  row date (past included), so a deleted song's id is never reused and history never re-links to another song.
- **C4 Duplicates.** Same `slug(title)` and same `slug(artist)` as another row is `song_exists` (create; update excludes
  the edited row). This also makes a retried create after a lost answer safe.
- **C5 Text rules (server and client identical).** Title and artist: a string, no C0/DEL/C1 control characters, trimmed,
  whitespace runs collapsed to one space, 1–100 characters, not starting with `=`, `+`, `-`, `@`, and a non-empty slug.
  Failures: `invalid_title`, `invalid_artist`. Key: `KEY_` (`invalid_key`); the client trims and upper-cases a leading
  `a`–`g` before `Key.parseOrNull`.
- **C6 Delete guard.** "Future jam" = the `futureJamIn_` definition: a `Jams` row with a known `estado` dated today or
  later (spreadsheet zone), i.e. the upcoming jam and every held-back jam. The server refuses `song_in_future_jam` when
  any such jam's tab has a row whose trimmed `id_tema` equals the id. The client pre-checks the same rule on the **raw**
  `JamsSnapshot` (`upcoming` + `heldBack`, `Setlist.Available` only) and shows the reason with the jam dates without
  sending; if a future setlist is not `Available` the client cannot know and lets the server decide.
- **C7 Key input.** A text field (`Tonalidad`, hint `Ej.: A, Bm, F#`), not the Próxima jam key grid (it lives in
  `:feature:next-jam`; moving it is out of scope).
- **C8 Writes.** One fair `Mutex` in the repository serializes catalog writes; each runs in `DataScope` from its first
  instruction (`async(start = UNDISPATCHED)`), so leaving the tab never cancels a write (only its result line is lost,
  the cost accepted by `admin-jams-tab`). Not `SetlistMutationQueue`: that engine is setlist-only.
- **C9 No pending-entry store.** The presenter holds the one in-flight operation and the last result; the list itself
  changes only from Room after the server's echo (no optimistic rows).
- **C10 Icon.** `TabIcon.CATALOG` → `Icons.Filled.PlayArrow` (I1: `material-icons-core` has no music icon; the label
  names the tab). **C11 Amber.** Only the default key of each row (`key` role); buttons are neutral, as `Nueva jam`.

## Acceptance Scenarios

1. **Musician.** Given admin mode is off (or not read yet), the bar has exactly `Próxima jam`, `Jams`, `Info`, as
   today (Asistente and Temas are both admin-only). If Temas is selected when the flag turns false, the shell selects
   Próxima jam.
2. **List.** Given admin mode, the bar is `Próxima jam`, `Jams`, `Temas`, `Info`, `Asistente`. Temas shows the cached
   catalog sorted by title then artist (accent/case-insensitive), a count, a search field filtering title or artist,
   loading/error/empty/staleness states and pull to refresh.
3. **Add.** When the admin fills `Crossroads` / `Robert Johnson` / `a` and confirms, `createSong` is sent with
   `{title:"Crossroads", artist:"Robert Johnson", defaultKey:"A"}` and no id; the server appends one row with
   `id`=`crossroads` (or `crossroads-robert-johnson` on a clash) and empty optional cells; the song appears from Room
   after the echo; `Tema agregado.` is announced.
4. **Edit.** Changing only the artist writes only `artista`; the id and every other cell stay. Same values: `Guardar`
   is disabled; a server `changed:false` is still a success.
5. **Delete refused locally.** Given the song is in the upcoming or a held-back jam's readable setlist, tapping delete
   shows `No se puede borrar «Crossroads»` naming the jam date(s); nothing is sent.
6. **Delete.** Given a song only in past jams, confirming deletes its row; past jams still show its title from the tab
   copies; the assistant and the add-song picker no longer offer it.
7. **Server refusal.** A `song_in_future_jam`, `song_exists`, `unknown_song` or `duplicate_id` answer shows the
   assertive failure card with its reason, changes nothing in Room, and (for `song_in_future_jam`) refreshes the jams.
8. **Outdated script.** `unknown_action` → `ScriptOutdated`: card with the update-the-script line and `Cerrar` only.
9. **Failures.** Offline / AccessRefused / Unavailable use the shared `write_failure_*` copy and `Reintentar`; a double
   tap on a confirm button sends once; while one write runs every submit and row icon is disabled.

- Client write: repository calls `AdminWriter.send`, maps `Refused` with `DataFailure.Service(UNKNOWN_ACTION)` to

- Dialogs, result line and failure card: the Jams tab (`admin-jams-tab`, `admin-edit-delete-jam`).
- Feature API surface: public screen resolves `koinInject()` and calls an `internal` overload (rule 21); previews in
  `*Preview.kt` (rule 22); copy in module `strings.xml` as `UiText`.

## Technical Approach

### Part A1 — Apps Script (`backend/apps-script/src/Post.js` only)

Append to `ACTIONS`: `createSong`, `updateSong`, `deleteSong`, `checkCatalogWrite` (all `write: true`). Add
`CATALOG_CHECK_TAB = '_prueba_catalogo'`, `MAX_SONG_TEXT_LENGTH_ = 100`, and helpers `normalizeSongText_(value, code)`,
`songSlug_`, `takenSongIds_(spreadsheet, catalogRows, columns)`, `findCatalogRow_(rows, columns, id)` (`unknown_song`,
`duplicate_id`), `appendCatalogRow_(sheet, columns, song, services)`, `writeCatalogCells_`, `deleteCatalogRow_`
(delete, flush, verify gone), `futureJamsWithSong_(spreadsheet, services, id)`.

- `createSong {title, artist, defaultKey}` → refusals in order: `invalid_title`, `invalid_artist`, `invalid_key`,
  `missing_tab`, `missing_header`/`duplicate_header` (via `catalogColumns_`), `song_exists`; then the id (C3), append the
  four mapped cells only (`id`, `titulo`, `artista`, `tono_default`; optional cells untouched), read back.
  Answer `{ok, song:{id,title,artist,defaultKey}}`. Other request fields are ignored.
- `updateSong {id, title, artist, defaultKey}` (all required) → `invalid_song` (`SONG_ID_`), the three text/key codes,
  missing tab/headers, `unknown_song`, `duplicate_id`, `song_exists`; equal values → `changed:false`, no write; else
  only the changed cells among `titulo`/`artista`/`tono_default`, read back. Answer `{ok, song, changed}`.
- `deleteSong {id}` → `invalid_song`, missing tab/headers, `unknown_song`, `duplicate_id`, then `song_in_future_jam`
  (message lists the dates; a future tab that cannot be mapped refuses with its header code), then delete the row and
  verify. Answer `{ok, id}`.
- `checkCatalogWrite` → on `_prueba_catalogo` only (leftover deleted first; deleted in `finally`): header + one marker
  row, `appendCatalogRow_`, `writeCatalogCells_`, `deleteCatalogRow_`, read back with `buildCatalog`. Never opens
  `Catalogo`. Answer `{ok:true}`.
- Header comment of `Post.js` gains an `admin-catalog-tab` paragraph (D-30). `Catalog.js`, `Code.js`, `Jams.js`,
  `Normalize.js` unchanged.

Node tests: new `backend/apps-script/test/catalog-write.test.js` (extend the `setlist.test.js` fake or copy its shape):
slug vectors; each refusal and that it writes nothing (write-op log empty); id clash → artist suffix; history id in a
past tab is taken; numeric suffix; `song_exists` case/accent-insensitive; update writes only changed cells and never
`tempo`/`etiquetas`/`dificultad`/`songsterr_id`/`id`; `changed:false`; delete refused for upcoming and held-back,
allowed for past-only; check action touches only `_prueba_catalogo`; router lists the four actions. Show the new tests
failing against the old `Post.js` first.
